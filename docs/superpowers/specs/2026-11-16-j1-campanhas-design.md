## 1. Objetivo

Hoje cada pessoa só vê as próprias fichas. Depois do 2.3, **o grupo joga junto**. O mestre cria uma campanha e manda um link, os jogadores entram por ele, e cada um vê a mesa conforme o papel: o mestre vê e edita as fichas da mesa, e o jogador vê o resumo das fichas dos outros jogadores e mexe só nas próprias. Serve aos dois objetivos da fase 2: uso real com o grupo e vitrine para entrevista.

**Escolhas do Arthur (2026-11-16):**
- **A ficha pode ficar sem campanha.** O painel atual vira "Minhas fichas". A ficha entra numa campanha quando é criada lá dentro ou quando o dono a leva depois. Se o jogador sai, é removido ou a campanha é apagada, a ficha volta para "sem campanha", sem perder nada.
- **As fichas do mestre ficam ocultas para os jogadores** (NPCs e monstros). Para o jogador, elas não existem (404).
- **O perfil `demo` fica para o 2.6.**
- **Só o dono exclui a ficha.** O mestre vê, edita e rola com as fichas da mesa, mas não as exclui.
- **Convite, papéis, telas e trava de edição** como propostos: código de 12 caracteres sem validade, renovar e desativar, prévia pública e aceitar só com login; um mestre por campanha, que não sai (apaga a campanha); telas Minhas campanhas, Campanha e Convite, mais um seletor de campanha na ficha; 409 ao gravar uma versão velha da ficha.
- **Abordagem A** (§2): a regra de acesso fica num componente central.

**Sucesso:**
- Duas contas, em duas abas: a primeira cria a campanha e copia o link, e a segunda entra por ele, criando a conta no caminho.
- Cada uma cria uma ficha na campanha. O mestre abre e edita a do jogador. O jogador não vê a ficha do mestre, e das fichas dos outros jogadores vê só o resumo.
- Renovar o convite derruba o link antigo. Tirar o jogador devolve a ficha dele a "sem campanha".
- Com a ficha aberta para edição nas duas abas, a segunda a salvar recebe o aviso de versão nova.
- Tudo funciona a 375 px e a 1280 px.

## 2. Abordagens (escolhida: A)

| | Como | Prós | Contras |
|---|---|---|---|
| **A. Regra central** ✔ | O `FichasDoUsuario` do 2.2 vira `AcessoAFicha`: carrega a ficha e o papel de quem está logado na campanha dela e decide entre liberar, 403 e 404. As campanhas têm uma regra parecida (`AcessoACampanha`). | Os 12 serviços da ficha não mudam. A matriz inteira é testada num ponto só. É fácil de explicar: "um único ponto de decisão, que já existia". | A regra vive no Java: um serviço novo que buscasse a ficha direto no repositório fugiria dela (hoje nenhum faz isso). |
| B. `@PreAuthorize` por rota | `@PreAuthorize("@acesso.podeEditar(#id)")` em cada método dos controllers | Idiomático do Spring, e a regra fica visível na rota | Cerca de 30 métodos anotados; a ficha é carregada duas vezes; o padrão é 403, que precisaria virar 404 para quem está fora |
| C. Row-Level Security no PostgreSQL | Políticas no banco que filtram as linhas pelo usuário da conexão | O banco garante mesmo se o código errar | Usuário passado a cada transação, convívio difícil com o pool de conexões, não distingue 403 de 404; demais para o projeto |

## 3. Dados: migração V11 (`V11__campanhas.sql`)

```sql
create table campanha (
    id             bigint        generated by default as identity primary key,
    nome           varchar(100)  not null,
    descricao      varchar(1000),
    codigo_convite varchar(12)   not null unique,
    convite_ativo  boolean       not null default true,
    criado_em      timestamptz   not null default now()
);

create table participacao (
    campanha_id bigint       not null references campanha (id) on delete cascade,
    usuario_id  bigint       not null references usuario (id),
    papel       varchar(10)  not null check (papel in ('MESTRE', 'JOGADOR')),
    entrou_em   timestamptz  not null default now(),
    primary key (campanha_id, usuario_id)
);
create unique index ux_participacao_um_mestre on participacao (campanha_id) where papel = 'MESTRE';
create index ix_participacao_usuario on participacao (usuario_id);

alter table ficha add column campanha_id bigint;
alter table ficha add constraint fk_ficha_participacao
    foreign key (campanha_id, dono_id) references participacao (campanha_id, usuario_id)
    on delete set null (campanha_id);
create index ix_ficha_campanha on ficha (campanha_id);

alter table ficha add column versao bigint not null default 0;
```

- **A chave estrangeira composta (escolha do Opus)** liga a ficha à participação do dono na campanha, e não só à campanha. Com isso, o banco garante a regra "a ficha só fica numa campanha da qual o dono participa". Quando a participação some (o jogador sai ou é removido, ou a campanha é apagada e leva as participações junto), o `on delete set null (campanha_id)` devolve as fichas a "sem campanha" sozinho, sem código no serviço. Isso exige o PostgreSQL 15 ou mais novo, e o projeto usa o 17 no compose, no Testcontainers e no Neon.
- O índice parcial `ux_participacao_um_mestre` garante no máximo um mestre por campanha. O serviço cria a campanha e a participação do mestre na mesma transação.
- As 5 fichas existentes ficam com `campanha_id` nulo e `versao` 0. Nenhum dado muda.
- **Entidades:** `Campanha` e `Participacao` (chave composta) num pacote `campanha`, como o `auth` do 2.2. Na `Ficha`, `campanhaId` entra como coluna simples, igual ao `donoId`, e `versao` entra com `@Version`. Na herança JOINED, a versão fica na tabela-raiz.

## 4. Regras de acesso

**Ficha:** a decisão segue esta ordem e fica toda no `AcessoAFicha`.
1. A ficha não existe → 404.
2. Quem está logado é o dono → libera.
3. A ficha está sem campanha → 404.
4. Quem está logado não é membro da campanha da ficha → 404.
5. É o mestre → libera (exceto excluir e mover: 403, ver a tabela).
6. É jogador, e o dono da ficha é o mestre → 404 (a ficha do mestre fica oculta).
7. É jogador, e a ficha é de outro jogador → 403.

| Ação na ficha | Dono | Mestre da campanha | Outro jogador | Fora da campanha |
|---|---|---|---|---|
| Ver completa, editar (`PUT`, `PATCH`), rolar, listas (itens, magias, ataques...), enviar ou apagar o retrato | sim | sim | 403 | 404 |
| Baixar o retrato (`GET /fichas/{id}/retrato`), que o cartão do resumo mostra | sim | sim | **sim** | 404 |
| Excluir a ficha | sim | **403** | 403 | 404 |
| Levar a outra campanha ou tirar da campanha | sim | 403 | 403 | 404 |
| Ficha do mestre, qualquer ação | (é o mestre) | — | **404** | 404 |

**Excluir só pelo dono (escolha do Arthur):** a §4 da fase 2 deixava o mestre excluir todas. Com a ficha podendo viver fora da campanha, ela é do jogador, e excluir é irreversível. O mestre que não quer mais uma ficha na mesa remove o jogador.

| Ação na campanha | Mestre | Jogador | Fora |
|---|---|---|---|
| Ver a campanha, os membros e as fichas da mesa | sim | sim (sem as fichas do mestre) | 404 |
| Criar ficha na campanha | sim | sim | 404 |
| Editar nome e descrição, excluir, ver e gerenciar o convite, remover jogador | sim | 403 | 404 |
| Sair | 409 "O mestre não sai da campanha. Para encerrá-la, exclua a campanha." | sim | 404 |

- Sem token ou com token inválido → 401, como hoje.
- Respostas em ProblemDetail, em português: 404 "Campanha não encontrada" e "Ficha não encontrada" (a de hoje), 403 "Você não tem permissão para isso nesta campanha.".
- `GET /fichas` ("Minhas fichas") continua listando só as fichas de que quem está logado é dono, em qualquer campanha ou em nenhuma.

## 5. API

**Campanhas** (pacote `campanha`):

| Rota | Quem | Resposta |
|---|---|---|
| `GET /campanhas` | logado | as campanhas de que participa: `[{id, nome, papel, mestre: {id, nome}, fichas}]`, em que `fichas` conta as fichas **que ele vê** na mesa |
| `POST /campanhas` `{nome, descricao}` | logado | 201 + `Location`; quem cria vira mestre; nasce com convite ativo |
| `GET /campanhas/{id}` | membro | `{id, nome, descricao, meuPapel, mestre: {id, nome}, convite}`; `convite` = `{codigo, ativo}` só para o mestre, e `null` para o jogador |
| `PUT /campanhas/{id}` `{nome, descricao}` | mestre | 200 com o mesmo corpo do `GET` |
| `DELETE /campanhas/{id}` | mestre | 204; as fichas voltam aos donos, sem campanha |
| `GET /campanhas/{id}/membros` | membro | `[{usuarioId, nome, papel, entrouEm}]`, o mestre primeiro e depois por ordem de entrada; **sem e-mail** |
| `DELETE /campanhas/{id}/membros/{usuarioId}` | mestre (remover jogador) ou o próprio jogador (sair) | 204; as fichas dele naquela campanha voltam a "sem campanha"; usuário que não é membro → 404; o alvo é o mestre → 409 (a mensagem de "Sair") se quem pede é o mestre, e 403 se é um jogador |
| `GET /campanhas/{id}/fichas` | membro | resumos das fichas que ele vê (§4): o mestre vê todas, inclusive as dele; o jogador, as dos jogadores. A contagem do `GET /campanhas` é o tamanho dessa lista |
| `POST /campanhas/{id}/fichas` | membro | o mesmo corpo de `POST /fichas`; 201 + `Location: /fichas/{id}`; dono = quem cria |

- `nome`: obrigatório, de 1 a 100 caracteres, sem espaços nas pontas. `descricao`: opcional, até 1000, e vazia vira `null`. JSON estrito, como no resto da API.

**Convite:**

| Rota | Quem | Resposta |
|---|---|---|
| `POST /campanhas/{id}/convite` | mestre | gera um código novo e ativa; o antigo deixa de valer na hora; 200 `{codigo, ativo: true}` |
| `DELETE /campanhas/{id}/convite` | mestre | desativa; 204 |
| `GET /convites/{codigo}` | **público** | `{campanhaId, campanha, mestre}` (só nomes); código inexistente, trocado ou desativado → 404 "Convite inválido ou desativado" |
| `POST /convites/{codigo}/aceitar` | logado | entra como jogador: 201 + `Location: /campanhas/{id}`; quem já é membro (inclusive o mestre) recebe 200; os dois com `{campanhaId}` |

- O código tem 12 caracteres de `A–Z`, `a–z` e `0–9` (cerca de 71 bits), gerado com `SecureRandom`. Em colisão com o `unique`, gera de novo. Não expira. O jogador removido pode voltar pelo mesmo link; para impedir isso, o mestre renova.
- O `SecurityConfig` libera só `GET /convites/*`. Aceitar exige token.

**Ficha:**
- `FichaResponse` ganha `versao`, `dono: {id, nome}` e `campanha: {id, nome}` (ou `null`). `FichaResumoResponse` mantém os campos de hoje (`id`, `sistema`, `jogador`, `personagem`, `idade`, `retratoVersao` e `recursos` com atual e máximo: PV, SAN e PE em Ordem, PV e PV temporário em D&D) e ganha `dono` e `campanha`. É o mesmo resumo para todos que o veem, como no cartão aprovado ("Kai (Arthur) PV 18/20 SAN 12/15"). As listagens continuam com **uma consulta só** (`ListagemSemNMaisUmTest`).
- `FichaRequest` (os dois sistemas) ganha `versao`: obrigatória no `PUT` (nula → 400 em `errors.versao`) e ignorada no `POST`, como o `id`. `dono` e `campanha` não entram no pedido (JSON estrito → 400).
- `PUT /fichas/{id}/campanha` `{campanhaId}` (número ou `null`), só o dono: leva a ficha a uma campanha da qual ele participa, ou a tira de uma. Uma campanha da qual o dono não participa → 404 "Campanha não encontrada". Responde 200 com a ficha.

## 6. Edição ao mesmo tempo (`@Version`)

- O `PUT /fichas/{id}` compara a `versao` do pedido com a do banco e, se forem diferentes, responde **409 "Esta ficha mudou enquanto você editava. Recarregue para ver a versão nova."**. A `ObjectOptimisticLockingFailureException`, a corrida entre dois pedidos simultâneos, vira o mesmo 409.
- Toda gravação da linha da ficha sobe a versão, inclusive a edição rápida de PV (`PATCH /recursos`), moedas, espaços de magia e a troca de campanha (`PUT /fichas/{id}/campanha`). Essas rotas **não** enviam versão, porque cada clique grava só o próprio valor. As listas (itens, magias, ataques, habilidades) e o retrato são linhas próprias e não mexem na versão.
- Nessas rotas sem versão, o conflito só acontece quando dois pedidos se sobrepõem no servidor (milissegundos), e não com cliques em sequência, porque cada pedido lê a versão atual. Se acontecer, a mesma exceção vira o mesmo 409 (um tratador só no `ApiExceptionHandler`), sem nova tentativa automática. A tela mostra a mensagem e recarrega a ficha (escolha do Opus: raro demais para justificar um laço de nova tentativa).

## 7. Frontend

**Rotas novas:**
- `/campanhas` (Minhas campanhas), com a lista (nome, papel, mestre e quantidade de fichas) e "+ Nova campanha" (nome e descrição).
- `/campanhas/:id` (Campanha):
  - as fichas da mesa, com os cartões do painel mostrando o dono. Só abre ficha quem pode: o dono ou o mestre. O cartão de outro jogador mostra só o resumo, sem link;
  - "+ Nova ficha aqui", que leva a `/fichas/nova?campanha=:id` e mantém a campanha até o formulário;
  - os membros. O mestre tem "Remover" nos jogadores, com confirmação, e o jogador tem "Sair da campanha", também com confirmação;
  - para o mestre: o convite (link completo, Copiar, Renovar com o aviso "o link antigo para de funcionar", Desativar; desativado mostra "Gerar novo link"), editar nome e descrição e excluir a campanha (confirmação: "As fichas voltam para os donos, sem campanha.").
- `/convite/:codigo` (Convite), **fora do guard de sessão:**
  - mostra a prévia (campanha e mestre);
  - sem sessão: "Entrar" e "Criar conta", que voltam ao convite pelo `?volta=` que o 2.2 já tem;
  - com sessão: "Entrar na campanha", que aceita e abre a campanha. Quem já é membro vê "Você já está nesta campanha" e um atalho para ela;
  - código inválido: "Convite inválido ou desativado. Peça um link novo ao mestre.".

**Mudanças:**
- Topo: links "Fichas" e "Campanhas". A 375 px, sem rolagem horizontal (o topo já é apertado desde o 2.2).
- Painel ("Minhas fichas"): o cartão mostra o nome da campanha, quando houver.
- Ficha:
  - o dono ganha no cabeçalho um seletor "Campanha", com as campanhas dele e "Sem campanha";
  - o mestre, na ficha de um jogador, vê "Ficha de {dono}" e não vê "Excluir";
  - 403 mostra "Você não tem permissão para abrir esta ficha.".
- Editar ficha: envia a `versao`. O 409 mostra o aviso com o botão "Recarregar", que traz a versão nova e descarta o que foi digitado.

O visual segue o do redesign (cartões, botões e cores atuais). Não há tela nova de estilo.

## 8. Testes

**Backend** (integração contra o PostgreSQL real, como hoje):
- **a matriz da §4 inteira**: cada linha das duas tabelas com dono, mestre, outro jogador, quem está fora e quem não tem token, em pelo menos uma rota de leitura, uma de escrita e uma de lista dentro da ficha;

- a migração V11 sobre dados da V10: as fichas ficam com `campanha_id` nulo, versão 0 e os mesmos donos;

**Frontend:** testes unitários dos serviços e das três telas novas, do seletor de campanha, do cartão sem link e do aviso de 409.

## 11. Riscos

| Risco | Mitigação |
|---|---|
| Link de convite vazado | O mestre renova o código e remove quem entrou |
| Um serviço novo buscar a ficha sem passar pelo `AcessoAFicha` | Regra registrada no ADR 0024 e no comentário do componente; o verificador procura `FichaRepository` fora dele |
| A versão sobe também na edição rápida, então o 409 pode aparecer mesmo sem conflito real no mesmo campo | Raro numa mesa; o aviso explica e o "Recarregar" resolve |
| Força bruta no código do convite | 71 bits tornam a tentativa inviável; o limite de pedidos fica para o 2.6, junto com o do login |
